# Frontend

`packages/web` is a Vite + React 19 single-page app. It talks to the API only through `/api/*` on the same origin: the Vite dev server proxies to the API on `API_PORT` (default 8080), and in production Nest serves the built app. There is no CORS and no API base URL. See the tooling skill for commands.

## Design reference

This skill is the design reference. The design is final: colours, type, spacing, radii and interactions are settled. Match the existing components and the values here; do not invent new ones. Where a value lives in code, the table names the file instead of repeating it. The later sections ("Styling", "UI components", "Media components" and the screen sections) describe how each piece is built.

### Not built

Decided against (architecture skill, settled decisions): Open folder (a browser cannot open a folder on the server), an About card and a location or genre line (MyTube stores no artist or album text), Open in Plex, playlists made in MyTube ("Yours"), a "Download full albums" rule or toggle, flat checkbox rules (rules are matcher trees edited in the builder), and a separate "Keep videos for" retention setting.

### Player

The in-app player (slice A: music; decided 2026-09-25). Code in `src/player-state.ts` and `src/components/player/`.

**Principles.** One thing plays at a time: starting anything replaces the queue; music and video never share one. Playback survives navigation: the bar and the card are fixed to the viewport and mounted once by `AppShell` (`PlayerLayer`). The bar is the only place with transport controls (no play or pause on tiles, the card or Now Playing), except the video frame itself (a click plays or pauses). Everything a queue is built from is on disk; a missing track only enters by an explicit "+" and shows muted (the transport steps over it). Not built: shuffle, repeat, queue reordering, drag-to-seek (tap to seek), scrub previews, chapters.

**Queue model** (`player-state.ts`, the `ui-state.ts` pattern: an external store, `usePlayerState()`; `usePlayerActive()` re-renders only when a queue appears or goes). `PlayerItem` `{ kind: 'music' | 'video', id, title, sub (artist / channel), album?, albumId?, when?, dur (s; the element's real duration replaces it), artUrl, fileUrl, missing? }`; `Player` `{ kind, queue, index, playing, pos (s), from }`; the state adds `cardOpen`, `nowOpen`, `buffering`, `error`, `resume` (a restored session, see "Session"), and the counters `load` (the element reloads the item from the start) and `seekRequest` (the element follows a seek).

- Actions: `playQueue(items, index, from)` (replaces, plays, opens the card unless Now Playing is open; a missing start moves to the next playable item), `appendToQueue(item)` (same kind: appended, `from` gets " +" once; otherwise a new one-item queue from "Queue"), `togglePlay` (play after the end restarts the last item), `setPlaying`, `next`, `prev`, `seek(pos)` (clamped), `seekBy(delta)`, `jumpTo(index)`, `closePlayer` (the bar's ×), `dismissCard`, `setNowOpen`, and the engine's `reportPosition`, `reportDuration`, `reportBuffering`, `reportError`. Helpers: `currentItem`, `upNext`, `queueLabel` (`3 of 10 · In Rainbows`), `playableAfter` / `playableBefore`.
- Transport: next at the end of the queue stops (`playing` false, `pos` = `dur`); previous past 4 s (`PREV_RESTART_SECONDS`) restarts the item, else goes back one (at the first, restarts); auto-advance on `ended`; keyboard ±10 s (`SEEK_STEP_SECONDS`).

- Audio graph (`useAnalyser.ts`): `<audio>` → `MediaElementAudioSourceNode` → `AnalyserNode` (fft 2048, smoothing 0.6) → `GainNode` → destination, built once by `connectAnalyser(element)`, which `AudioEngine` calls before every play: it builds the graph only while the page has a user activation (the click that started playback; a source node routes the element's sound through the context, so a context the browser keeps suspended would mute it) and resumes a suspended context on every play. Without `AudioContext`, or when building throws, nothing is built and the element plays as before. `useAnalyser()` returns the reader the loop polls (null until the context runs). **The analyser reads the full signal; volume is a gain node after it** (Thomas's request: turning the sound down must not flatten the bars): while the element plays through the graph it stays at `volume` 1 and unmuted, and `applyAudioVolume` (`audio-output.ts`) sends the store's level to `setOutputVolume` (0 when muted, `setTargetAtTime` with a 15 ms time constant against clicks); without a graph it sets the element's `volume` and `muted` as before. `AudioEngine` applies it on every change, every load and right after `connectAnalyser`, so the first click-started play moves the level onto the gain. `VideoEngine` keeps the element's volume (no analyser there).
- Amplitudes (`createAmplitudeState`): playing with an analyser, `getByteFrequencyData` bins from 30 Hz to 16 kHz map to the bars logarithmically (`logBinRanges`: at least one bin each, in order), the mean of each range weighted from ×0.8 (bass) to ×1.8 (treble), since music carries less energy up there; `beat` = the energy under 150 Hz normalised against its slowly decaying peak (0.7–1.15). Bars rise by half the gap a frame and fall with a 0.8 decay. ### Tabs: the `navigation.ts` contract

`src/navigation.ts` is the single source for tabbed sections. The shell, the tab pills and the screens import from it; never repeat a tab id or label as a string literal elsewhere.

- `MUSIC_TABS`, `VIDEO_TABS`, `SETTINGS_TABS`: readonly tuples of the lowercase URL ids, in display order.
- `MusicTab`, `VideoTab`, `SettingsTab`: their union types.
- `DEFAULT_MUSIC_TAB` (`albums`), `DEFAULT_VIDEO_TAB` (`videos`), `DEFAULT_SETTINGS_TAB` (`general`).
- `TAB_LABELS`: display label per tab id (`albums` → `Albums`). The ids are unique across sections.
- `TAB_ICONS`: icon component per tab id for the tab pills (see Icon registry).
- `parseTab(tabs, value)`: the tab, or `undefined` when `value` is not one of `tabs` (exact, lowercase).

### Typed params and redirects

- A `$tab` route declares `params: { parse, stringify }`. `parse` returns `{ tab: MusicTab }` (annotate the return type), so `Route.useParams()` and `Link`'s `params` are typed with the union.
- An unknown tab never renders: `parse` throws `redirect({ to, params: { tab: DEFAULT_… }, replace: true })`. The router runs `parse` while matching, before `beforeLoad`, and treats a thrown redirect as a redirect, so this is the one place the check lives.
- A bare section (`/music`) has a `*.index.tsx` route with only `beforeLoad: () => { throw redirect({ …, replace: true }) }`.
- Always `replace: true` on these redirects so browser back skips the URL that redirected.
- Link to a tab with `<Link to="/music/$tab" params={{ tab: 'tracks' }}>`; link to a section with its default tab rather than the bare path, which saves a redirect.

### Search params

State that should survive a reload or a shared link lives in the URL search params, validated by the route's `validateSearch`. `/music/$tab` has the Tracks tab's `q`, `filter`, `sort` and `dir` (`TrackSearch`): `parseTrackSearch` (in `components/library/track-list.ts`, tested) keeps valid values and drops invalid ones and defaults, so the plain `/music/tracks` is All sorted by Added descending and a hand-edited URL never breaks the page. Every field is optional, so links to the other tabs need no `search` (and drop it). Screens read with `useSearch({ from: '/music/$tab' })` and write with `useNavigate({ from: '/music/$tab' })` and `resetScroll: false`; typing replaces the history entry, a filter or sort click pushes one (browser back undoes it).

### Adding a tabbed section

1. Add `FOO_TABS`, `FooTab`, `DEFAULT_FOO_TAB` and the labels to `navigation.ts`, and cover them in `navigation.spec.ts`.
2. Add `foo.$tab.tsx` with the `params` block above and `foo.index.tsx` with the redirect.
3. Run `pnpm dev` or `pnpm build` so the plugin regenerates `routeTree.gen.ts`, and commit it.

## Data fetching

- React Query for all server state. `queryKey` arrays name the resource, for example `['health']`, `['channels', id]`.
- Plain-text endpoints (job logs) go through `apiGetText(path)`.
- Call the API through `apiGet(path, Schema)`, `apiPost(path, body, Schema)`, `apiPatch(path, body, Schema)` and `apiDelete(path)` from `src/api/client.ts`. They validate the JSON against the shared Zod schema and throw `ApiError` (`status`, raw `body`, `json()`) on non-2xx.
- Show a failed request with `apiErrorMessage(error, fallback)`: the API's `message` as a sentence, with validation `issues` and a yt-dlp `reason` appended; `fallback` for network errors and non-JSON bodies.
- A screen whose query failed shows `ErrorState` (see "Empty and error states"); `loadErrorDetail(error)` in `client.ts` is its second sentence: the API's message, `The server answered 502.`, `The server did not answer.` (fetch rejected) or `The answer was not in the expected shape.` (Zod).
- Never hand-write response types in the web package. Import schemas and types from `@mytube/shared`.

### Theme

- `data-theme="light" | "dark"` on `<html>` forces a theme. Without it, `prefers-color-scheme` decides. The dark values live in `styles.css` twice (attribute and media query); keep them identical. `red`, `ok` and `white` are the same in both themes.
- Components never branch on the theme and never use the `dark:` variant; the tokens swap underneath them.
- `useTheme()` from `src/theme.ts` returns `{ theme, resolvedTheme, setTheme }`. `theme` is the choice (`'light' | 'dark' | 'system'`), `resolvedTheme` what is on screen (`'light' | 'dark'`), `setTheme(choice)` sets the attribute and caches the choice in localStorage under `mytube.theme` (`system` clears it). An inline script in `index.html` applies the cached choice before first paint.
- **The source of truth is the settings table** (`general.theme`, see the architecture skill). The root layout calls `useThemeFromSettings()`, which applies the stored theme with `setTheme` once settings load. Screens change the theme with `useUpdateSettings().mutate({ general: { theme } })`, which calls `setTheme` optimistically and reverts it if the save fails. A bare `setTheme` (as on `/dev/tokens`) only lasts until the next settings load.
- Settings → General offers Light, Dark and **System**, so the user can go back to following the device.

### Focus and motion

Defined once in `styles.css`; components never write their own `transition` or outline values.

- **Focus:** a global `:focus-visible` rule gives every focusable element the ring (2px red outline, offset 2px) without opting in. Utilities for the variants: `focus-ring` (the same ring, explicit and immune to `outline-none`), `focus-ring-inset` (offset -2px, for items inside a clipping container: tab pills, nav rows, the channel link in a tile chin) and `focus-ring-overlay` (rings the element when its descendant marked `data-overlay` has keyboard focus; for overlay-button tiles) and `focus-ring-on-red` (the ring in white, for controls on the red player bar). ## Sources screens

### Hooks: `api/sources.ts`

- Keys (`sourceKeys`): `['sources', 'list', library ?? 'all']` per list, `['sources', 'detail', id]` per source; everything starts with `['sources']`.
- `useSources(library?)` (`GET /api/sources[?library=]`), `useSource(id)` (`GET /api/sources/:id`; a 404 is not retried; ids below 1 never fetch).
- `useResolveSource()`: mutation, `POST /api/sources/resolve` → `ResolvedSource`. A mutation, not a query, because it follows typing and must not be cached; callers ignore answers whose `variables` are no longer the link in the box.
- `useCreateSource()`: `POST /api/sources`; seeds the detail cache and invalidates the lists. `conflictSourceId(error)` reads `sourceId` from a 409 (`SourceConflict`).
- `useUpdateSource()`: `{ id, patch: UpdateSource }` → `PATCH /api/sources/:id`; the answer replaces the source in every list and the detail cache, and a rules change invalidates `['activity']` (a revalidation is queued).

With several toggles in flight (shared mutation key) only the last settles the caches. Screens show "Could not change the subscription. The previous state is back." while `isError`.
- `useCheckSource()`: `POST /api/sources/:id/check` (202 `Job`), then invalidates `['activity']`; the album page's Check for changes.

### Rule builder: `components/rules/`

The rules of a source are one matcher tree (architecture skill, settled decisions; backend skill "Matchers"). There is no checkbox mode.

- `matcher-draft.ts` (pure, `matcher-draft.spec.ts`): the editing state. `DraftGroup` `{ kind: 'group', id, gate: 'and' | 'or', negated, items }` and `DraftLeaf` `{ kind: 'leaf', id, type, negated, text, pattern, date, days, seconds, status, channel, position }` (every leaf keeps every parameter, so switching a condition's type and back loses nothing). There is no NOT gate (decided by Thomas: NOT over several children reads badly and the toggles express it, since NOT(A OR B) = AND(NOT A, NOT B)); every node, group or condition, has a NOT toggle (`negated`) that wraps it in the schema's `not`. Loading a tree folds each `not` into the toggle of the node it wraps, so a `not` around a group shows as the group's toggle, one around a condition as the condition's, and double negations cancel. `draftFromMatcher(matcher)` (the root is always a group) and `matcherFromDraft(root, { playlist })` → `{ ok, matcher }` or `{ ok: false, error }` (the first problem: empty text, invalid regex via shared `regexError`, missing date, out-of-range numbers, an empty nested group, an empty root other than AND, a playlist-only condition outside playlists, then the shared schema's depth and size limits). `nodeError(node, { root, playlist })` for inline messages. Edits return a new root and keep untouched nodes' identity: `addNode`, `removeNode` (never the root), `moveNode` (±1 within its group; no UI yet), `updateLeaf`, `setGate`, `canAddGroup` (stops offering "Group" before the depth limit). `setNegated` flips any node's toggle. `newLeaf()` is an empty "Title contains", `newGroup()` an OR with one empty condition. `LEAF_OPTIONS` / `leafOptions(playlist)`, `LIVE_STATUS_OPTIONS`, `GATE_LABELS` (`AND`, `OR`) and `groupHint(gate, negated)`: all of / any of these, and with NOT not all of / none of these. The root may be negated too; an empty root is only valid as a plain AND.
- `MatcherBuilder` (`value`, `onChange`, `playlist`, `label?` default "Rules"): a labelled group. Each group: its NOT toggle, a small `TabPills` (AND / OR) with its hint in Space Mono (`groupHint`), a × (`IconButton` sm, `CloseIcon`) on nested groups, then its items indented behind a 2px `line` left border, and outlined **Condition** (`AddConditionIcon`) and **Group** (`AddGroupIcon`) buttons. A condition row is a grid: a NOT toggle (a small Space Mono pill with `aria-pressed`, red when on), the type `Select` with its value control (text `Input shape="value"` for title / regex / channel, a date input, `NumberInput` with a `days` / `seconds` unit, a live status `Select`; nothing for "Is a short" and "Is members-only"), which wraps under the type when the row is too narrow, and a × pinned to the top right. Empty fields are reported once above the modal footer; wrong values (a bad regex, a range) inline in red with `aria-describedby`. Adding moves focus to the new condition's type select, removing to the group's Condition button. Fits the 560px modal and 375px (no horizontal overflow; deep rows wrap).

## App shell

`src/components/shell/AppShell.tsx` is the layout, rendered by `routes/__root.tsx` around `<Outlet />`. `/dev/*` pages are left outside it and render their own `<main>`.

- **Wide (`wide:`, 760px and up):** `Sidebar` (232px, sticky, full height, `side` bg, `line` right border) with the lockup, the five `NavItem`s, a spacer, the "+ Add to library" button and a footer slot. While the player bar is up (`playerBar`), the sidebar's bottom padding grows by `bar height + 32px`, so the Add button and the yt-dlp lines sit above the full-width bar. Main is fluid with `min-width: 0`.
- **Add buttons:** the top bar "+" is `ui/IconButton` (`tone="red"`, `size="lg"`). The sidebar pill is `ui/Button` (`variant="primary"`, `size="xl"`, `fullWidth`, `PlusIcon`).
- **Narrow:** the sidebar is hidden, `TopBar` (sticky, lockup + round red "+") sits at the top of main, `TabBar` (five sections, fixed to the bottom, safe-area aware) sits below everything.
- **Main owns the outer padding and section rhythm:** padding 32px 40px 64px wide and 0 16px 96px narrow (the 96px clears the tab bar; while the player bar is up the bottom padding is `64px + bar height + 40px` wide and `96px + bar height + 40px` narrow, the bar publishing its height as `--player-bar-height`), and a flex column gap of 28px wide / 20px narrow between page sections. Pages set **no** outer padding, margin or max width on their root; they render their sections (header, tab pills, grid, ...) as direct children, usually through a fragment. Content max widths such as the Settings column (760px) belong on the section itself.
- **Props from data:** `activityCount` (active downloads; the Activity badge shows when above 0, in both the sidebar and the tab bar) and `sidebarFooter` (a node, normally `<SidebarFooter version status />`, which renders `yt-dlp <version>` over the status line). The root passes `useActivitySummary().data?.activeDownloads` (download jobs queued or running), and `<YtdlpFooter />` (`components/shell/YtdlpFooter.tsx`), which feeds `SidebarFooter` from `useYtdlpStatus()`: `yt-dlp <installedVersion or —>` over `<state label> · auto-update <on|off>` (`loading…` / `status unavailable` before data). `SidebarFooter` splits the status line at `·` and keeps each part on one line, so a long status wraps at the separator.

### Nav sections and the active state

- `navigation.ts` holds `NAV_SECTIONS` (`home`, `music`, `video`, `activity`, `settings`, in display order), `NAV_SECTION_LABELS` and `sectionOfPath(pathname)`.
- Active state is **section-level**: `sectionOfPath` maps a pathname to its section by the first path segment, so `/music/tracks` keeps Music active and `/video/channel/abc` keeps Video active; Home matches `/` only. The shell reads it through `useActiveSection()` in `components/shell/sections.tsx` and sets `aria-current="page"` on the active link. Do not use `Link`'s `activeProps` for the nav: the section links point at the default tab (`/music/albums`), which would not match the other tabs.
- Section links go to the default tab (`SECTION_LINKS` in `sections.tsx`), never to the bare section path.

### Global UI state: `ui-state.ts`

A tiny external store (the `useSyncExternalStore` pattern from `theme.ts`) for dialogs that any screen can open. `useAddModal()` returns `{ open, openAdd, closeAdd }`. Every Add button (sidebar, top bar, and later the empty states) calls `openAdd`; `AppShell` mounts `AddSourceModal` only while `open` is true (so each opening starts empty) and passes `closeAdd` as its `onClose`. `useJobLogViewer()` returns `{ jobId, openJobLog, closeJobLog }`: View log links call `openJobLog(jobId)`; `AppShell` mounts `LogViewerModal` keyed by the job while `jobId` is set. Add more global dialogs here rather than threading state through props.

## Empty and error states

By design they are plain muted Archivo 14 text. Every screen uses the two named components from `components/ui/` (never a hand-written `<Body muted>` for these):

- **Empty:** `EmptyState` with one or two dry sentences. Copy in use: Home "Nothing downloaded yet. Add a channel or an artist to get started." (with the Add to library button, the only one) or "Nothing downloaded in the last 14 days."; Videos and the channel page "Nothing downloaded yet."; Channels "No channels yet. Add one with + Add to library."; Artists, Albums, Playlists "No … yet. Add … with + Add to library."; Tracks "No tracks yet. …" and "No tracks match."; Activity "Queue is empty." and "No history yet."; channel page 404 "This channel is not in your library."; album page 404 "This album is not in your library."; artist page 404 "This artist is not in your library.", "Nothing of this artist is in your library yet." and "Every release is in your library.".
- **Failed request:** `ErrorState what="<the thing>" {...fromQuery(query)}` when `loadFailed(query)`, that is only while the query has no data (a failed background refetch or poll keeps what is on screen). Retry refetches. Settings uses it in `SettingsTab` ("Could not load the settings.").
- **Render error:** `defaultErrorComponent: RouteError` in `main.tsx`. A route that throws renders `Could not show this page. <message>` with Retry (resets the boundary and invalidates the router) inside the app shell.
- Loading lines stay `StatusLine` ("Loading tracks."); there are no spinners and no toasts.
- `/dev/components` shows both components; `states.spec.tsx` renders them with `react-dom/server`.

## Component structure

- **Pages and semantic components compose named components.** A page should read like the design: `<PageHeader>`, `<TabPills>`, `<TileGrid>`, `<StatCard>`. Long Tailwind class lists do not belong on pages, layouts or other high-level components.
- **Class lists live inside the leaf components** that implement the design system (`src/components/**`), and those use the token utilities (`bg-surface`, `text-muted`, `rounded-tile`, `text-section-label`) rather than raw values.
- **Type roles are components too.** Wrap the type utilities in small components such as `<PageTitle>`, `<SectionLabel>` and `<Meta>` so screens never repeat `text-h1` or `text-meta`.
- A component takes semantic props (`variant="primary"`, `subscribed`, `incomplete`), not class names, except an optional `className` for layout placement by the parent.

## Conventions

- Function components, hooks, no class components.
- Imports use no file extensions (bundler resolution).
- Component library conventions: see "UI components" above.
